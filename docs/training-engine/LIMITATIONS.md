# Support boundaries and remaining limitations

- Healthy adults ≥18 only, with an explicit healthy status. Active injury, relevant medical conditions, rehabilitation, pregnancy-specific needs and current pain return unsupported. No diagnosis, screening certification, treatment, or rehabilitation is attempted. Lack of a reported condition does not certify medical fitness.
- Power/velocity training, Olympic lifts, timed isometrics, special partial-ROM prescriptions, supersets, BFR, competition peaking and rehabilitation are not automatically programmed. The domain can evolve without pretending these capabilities exist today.
- The current audit contains 443 `unknown` exercise-type records and a 468-record unknown/low-confidence/conflict review queue. There are 84 sampled-frame-plus-text reviews: 72 fully reviewed across all core programming fields, 12 partial, and 0 stale; 1,240 records still use deterministic rule fallback. All source exercises remain accessible; automatic suitability is conservative (`allowed` 666, `specialized_only` 35, `manual_only` 623). Eight reviewed records retain honest source/media conflict tags. Name/instruction rules are transparent approximations, not verified professional curation. Equipment detection cannot guarantee complete ancillary requirements, and source technique instructions are unverified. The next data task remains systematic review of the queue and common rule-only families.
- Automatic planning currently supports resistance exercises tracked by external load, assistance, bodyweight, or qualitative band resistance. Band prescriptions cannot infer kilograms or compare one band to another. Repetition-only, timed, distance, unknown, and non-resistance records stay catalogue-visible but outside ordinary automatic programming until their prescription semantics exist.
- The muscle vocabulary combines distinct regions (e.g. lats and rhomboids; all deltoid heads). Effective-set accounting cannot resolve regional hypertrophy. Indirect credit 0.5 and broad direct roles are replaceable policy, not measured stimulus fractions. Drop/other sets are retained in logs but excluded from ordinary set equivalents pending a defensible policy.
- Workload half-life, scoring weights, targets, set-per-session guidance, timing, e1RM confidence and reduced-volume triggers are engineering heuristics. No predicted gains, injury risk, measured fatigue or clinical recovery scores are produced.
- Bounded search may fail to find an existing feasible program. Infeasible means no valid candidate found under this implementation/budget, not a mathematical impossibility proof. Small exercise pools often return partial programs. Hard minimums are honored or explicitly fail; no solver is included.
- Default beam width 3 favors interactive latency. Wider beams are not guaranteed to produce a greater final score because partial-week pruning can discard a narrow-beam path before bounded terminal local improvement; the benchmark records these cases. Single-equipment minimum datasets can provide incomplete pull/hamstring coverage; these deficits are reported. Time is a conservative estimate and cannot guarantee real gym elapsed time. No asynchronous UI worker is wired up yet.
- e1RM is limited to low-rep external-load sets with known effort. No cross-station/exercise/bodyweight/assistance inference exists. Numeric progression requires station identity, load basis and an explicit achievable grid. Bodyweight/repetition progression cannot identify the correct harder variation without more metadata.
- History is observational. Unknown log coverage does not imply no training. Volume targets are individualized only with sufficient complete history; soreness is self-report. One session cannot establish tolerance. No wearable signal is silently imported.
- Completed history uses one canonical session record per planned session, and unique set IDs; a persistence adapter must merge partial updates rather than append duplicate observations. Complementary left/right records may share a planned-set reference; repeated same-side or mixed paired/single-side references are rejected. Each paired unilateral set covers both sides; separate left/right records contribute half group volume. Bilateral group accounting does not describe left/right asymmetry.
- Adaptation returns a revision of **future slots**, linked to the source program. Past plans stay untouched; actual sets remain in history. Callers must retain this lineage. Remaining-week validation adds actual volume when enforcing original weekly bounds. It does not fill all missed volume; sometimes the result is partial or no feasible future slot exists. A different schedule can require source-slot matching by weekday, then positional fallback.
- Phase support is base and reactive reduced volume. Future weeks repeat a template until observed history justifies changes. Advanced strength peaking and long-term individual dose optimization are future work.
- Content fingerprints are non-cryptographic 32-bit identifiers for reproducibility, not security guarantees. Storage should use a separate globally unique record key and retain the content fingerprint. No identifiers encode private profile information directly, but hashing is not anonymization.

## Persistence and frontend migration boundary

The existing workout store records exercise IDs, timestamps, duration and estimated calories. `adaptLegacyWorkout` copies only observed session/exercise identity and duration; it creates **zero sets**. It cannot recover reps, load, RIR or effective training volume from those records. Future persistence must add versioned set logs, planned-session/set lineage, canonical units, station/basis/load-grid configuration and explicit history coverage. Do not backfill fictional sets or destructively migrate old workouts. Keep store/schema migrations, forms, React hooks, Apple Health, Web Workers and UI explanations as separate work.

A future natural-language or HealthKit adapter may supply validated structured input; all planning remains deterministic and local. No runtime networking, AI, backend, cloud sync, React or Zustand integration was added.
